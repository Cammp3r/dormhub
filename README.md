# DormHub — інтерфейс гуртожитку

Десктопний застосунок на Python (CustomTkinter) для гуртожитку: чати, оголошення,
вакансії та заявки на ремонт.
Усі записи застосунку читаються з PostgreSQL. Для доступу до даних використовуються
Peewee та параметризовані SQL-запити. Локальних мок-даних і підстановки
демонстраційних записів при помилці БД немає. Порожні таблиці відображаються як порожні списки.
Після запуску введіть ім’я та прізвище наявного активного користувача PostgreSQL.
Пробіли на початку й у кінці ігноруються, регістр перевіряється засобами PostgreSQL.
Неоднозначні збіги не допускаються до входу.
Кнопка «Вийти з акаунта» повертає на екран входу.

Адміністратори визначаються за таблицею `dorm_admins`: у профілі відображається
«Адміністратор». У коді немає фіксованих користувачів чи ID адміністраторів.
Вхід за ім’ям і прізвищем — тимчасовий режим без пароля.

## Запуск на Windows

1. Встановіть Python 3.10+ з python.org (під час встановлення поставте галочку **Add python.exe to PATH**).
2. Розпакуйте папку й двічі клацніть **`run.bat`**. Перший запуск сам створить середовище й встановить бібліотеку.

Або вручну в терміналі:
```
pip install -r requirements.txt
python main.py
```

## Підключення PostgreSQL

Для **нової або наявної бази** створіть базу PostgreSQL і запустіть:

```
.venv\Scripts\python migrate.py
```

Міграції з каталогу `migrations/` виконуються послідовно та реєструються в таблиці
`schema_migrations`. Повторний запуск пропускає вже застосовані версії.
На наявній базі початкова схема фіксується як базова, після чого застосовуються
лише наступні міграції. Дані користувачів, кімнат і повідомлень не видаляються.
`db.sql` та `db_update.sql` залишені як пояснювальні файли для старого способу
запуску й більше не виконують SQL-операцій.

Створіть файл `.env` зі своїми параметрами підключення:

```
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=dormhub
DB_USER=postgres
DB_PASSWORD=ваш_пароль
```

Файл `.env` не потрібно додавати до Git.

У порожній базі створіть першого адміністратора:

```
python setup_admin.py
```

Для додавання кількох повторно безпечних тестових студентів виконайте:

```
python seed_demo.py
```

Скрипт використовує гуртожиток першого адміністратора, не створює адміністраторів
і не дублює тестові записи при повторному запуску.

Скрипт запитає справжній номер і адресу гуртожитку, ім’я, прізвище та email адміністратора.
Усі введені дані зберігаються однією транзакцією. Якщо адміністратор уже існує,
повторне початкове налаштування заборонене. Увійдіть за введеними ім’ям і прізвищем;
мешканців та кімнати можна додати в адміністративному кабінеті. Факультети, навчальні
курси, вакансії та паркомісця наразі додаються безпосередньо у відповідні таблиці через pgAdmin.

Категорії й статуси звернень читаються з `request_categories` та `request_statuses`.
Їх можна змінювати через pgAdmin; нові значення з’являться після оновлення сторінки.
У `request_statuses` рівно один статус має мати `is_initial = TRUE`; його отримують
нові звернення. Назви, які вже використовуються, захищені зовнішніми ключами;
перейменування каскадно оновлює звернення та їхню історію.

## Оголошення, вакансії та адміністрація

Після оновлення виконайте `pip install -r requirements.txt` (додано `tzdata` для
київського часу у Windows), запустіть `migrate.py` і запустіть програму.

- **Оголошення:** кожна публікація адресована конкретному гуртожитку через
  `dorm_id`; мешканці бачать лише оголошення свого гуртожитку, а адміністрація
  створює, редагує та видаляє оголошення свого гуртожитку.
- **Мої звернення:** заселений мешканець створює ремонтне звернення й бачить свої
  звернення, відповіді та історію статусів, зокрема після переселення.
- **Вакансії:** перегляд вакансій і статус власної заявки в одній вкладці
  «Вакансії».
- **Адміністрування:** доступне лише адміністраторам із таблиці `dorm_admins`.
  Вкладки: «Гуртожиток», «Мешканці», «Кімнати», «Поселення», «Звернення».
  Адміністратор може змінити номер і адресу свого гуртожитку, поверх кімнати,
  місткість, доступність кімнати та стан кожного окремого місця.
  Мешканця спочатку додають без кімнати, потім поселяють. Є пошук, фільтри за кімнатою
  редагування даних і поселення без зміни ролей.
  Кімнати мають місткість та доступність для поселення. Кімнату можна закрити для
  нових поселень, не виселяючи поточних мешканців.

Права перевіряються в операціях доступу до даних. Адміністратор керує лише своїм
гуртожитком; змінювати ролі через ці форми не можна. Поселення, переселення й виселення
виконуються транзакційно, з історією, відповідальним адміністратором і причиною;
подвійне поселення на місце захищене унікальним індексом і блокуванням записів.
`students.room_id` і `students.place_id` оновлюються в тій самій транзакції, тому кімната,
місце, сусіди й доступ до чату відповідають поточному поселенню. Місця створюються
автоматично відповідно до місткості кімнати; зайняте або історично використане місце
не можна видалити зменшенням місткості.
При створенні кімнати автоматично створюється її чат. Оновлення списків — кнопкою
«Оновити» або при переході між вкладками.

Факультети й навчальні курси залишаються в PostgreSQL для майбутніх чатів
гуртожитку, факультету та курсу, але окремих розділів у цьому UI немає.
Звернення мають окремі таблиці `maintenance_requests` і `request_status_history`;
`applications` і надалі містить лише заявки на вакансії. Продовження строку проживання,
призначення майстрів і сповіщення ще не реалізовані.
Тимчасовий вхід за ім’ям і прізвищем та пряме підключення до БД залишаються поточними
обмеженнями застосунку.

## Структура

```
main.py                 точка входу
setup_admin.py          початкове створення адміністратора з введених даних
db.sql                  довідка про перехід на міграції
migrations/             послідовні міграції схеми зі збереженням даних
migrate.py              безпечний запуск міграцій PostgreSQL
data/
  repository.py         функції доступу до PostgreSQL
ui/
  app.py                головне вікно, бічне меню, перемикання сторінок
  theme.py              спільні кольори/шрифти
  module_a/             Люди і проживання: profile.py, room.py
  module_c/             Паркінг та інші розділи
```

Кожен з команди працює у своїй папці `module_*` і у своєму розділі `repository.py`,
тому конфліктів у Git майже не буде.
