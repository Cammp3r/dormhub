# DormHub — план MVP і курсової роботи
## 1. Межі MVP

DormHub — система адміністрування гуртожитку для мешканців і адміністрації.
У межах MVP підтримуємо один гуртожиток у повному робочому циклі, але модель
даних і перевірки доступу не повинні обмежуватися одним гуртожитком.

Основний сценарій приймання:

1. Головний адміністратор налаштовує гуртожиток і призначає адміністратора.
2. Адміністратор створює мешканця без автоматичного поселення.
3. Адміністратор поселяє мешканця на вільне місце.
4. Мешканець входить і бачить профіль, кімнату, сусідів та оголошення.
5. Мешканець створює ремонтну заявку.
6. Адміністрація опрацьовує заявку та змінює її статус.
7. Адміністрація продовжує проживання або виселяє мешканця.

До MVP входять:

- акаунти та права доступу;
- гуртожитки, кімнати й окремі місця;
- поселення, переселення, продовження та виселення;
- ремонтні заявки;
- оголошення;
- текстові кімнатні чати;
- вакансії разом із переглядом власних заявок;
- база даних і SQL-функціональність, необхідні для курсової роботи.

Факультети й навчальні курси залишаються в БД як основа для майбутніх чатів
факультету та курсу, але їхні UI-розділи й поточний функціонал прибрані.
Події, платежі, мобільний клієнт і розширені інтеграції до MVP не входять.

## 4. Обов’язкові SQL-сценарії курсової

Кількість сценаріїв треба підтвердити для кожного учасника команди: кожен
учасник має виконати щонайменше один сценарій створення, один оновлення, один
видалення, два прості SELECT і один аналітичний запит.

### 4.1. Створення

- [ ] Описати та закріпити щонайменше один сценарій створення кількох
  пов’язаних сутностей в одній транзакції.
- [ ] Продемонструвати валідацію, зовнішні ключі, унікальні обмеження,
  повний результат із пов’язаними даними та rollback при помилці.
- [ ] Використати як приклад створення мешканця, кімнати з місцями або
  ремонтної заявки.

### 4.2. Оновлення

- [ ] Описати щонайменше один сценарій оновлення на основі поточного стану.
- [ ] Продемонструвати `UPDATE ... WHERE`, перевірку умов, транзакційність
  і оптимістичне або песимістичне блокування.
- [ ] Перевірити race condition для одночасного поселення на одне місце.

### 4.3. Видалення

- [ ] Описати щонайменше один сценарій hard delete або soft delete.
- [ ] Перевірити референтну цілісність, каскадне видалення та очищення
  пов’язаних записів.
- [ ] Документувати видалення оголошення або інший обраний сценарій видалення.

### 4.4. Прості SELECT

- [ ] Підготувати щонайменше два прості SELECT-сценарії на кожного учасника.
- [ ] У сценаріях використати `WHERE`, прості `JOIN`, `ORDER BY` і
  `LIMIT/OFFSET`.
- [ ] Додати пошук і фільтрацію мешканців або заявок як задокументовані приклади.

### 4.5. Аналітичні SELECT

- [ ] Реалізувати щонайменше один аналітичний запит на кожного учасника.
- [ ] Використати бізнес-питання предметної області, наприклад статистику
