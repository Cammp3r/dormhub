# DormHub — план розвитку системи адміністрування гуртожитків

## 1. Задум продукту

DormHub об’єднує роботу адміністрації гуртожитків і повсякденні потреби мешканців в одному застосунку. Орієнтир за ідеєю — сервіс проживання на кшталт Unite Students; цей план описує власні функції DormHub, без припущень про точний набір можливостей іншого сервісу.

Основний процес: адміністрація додає гуртожиток і кімнати, запрошує мешканця, поселяє його на конкретне місце, опрацьовує звернення, публікує оголошення та оформлює продовження проживання або виселення. Мешканець бачить свою кімнату, сусідів, повідомлення й стан своїх заявок.

Перший робочий реліз має підтримувати один гуртожиток повністю, а структура даних і права доступу — одразу враховувати кілька гуртожитків.

## 2. Що вже є

- [x] Десктопний інтерфейс Python / CustomTkinter.
- [x] PostgreSQL і функції доступу до даних у `data/repository.py`.
- [x] Тимчасовий вхід за ім’ям і прізвищем, вихід з акаунта.
- [x] Визначення адміністратора за `dorm_admins`, позначення у профілі.
- [x] Перегляд і редагування основних полів профілю.
- [x] Перегляд своєї кімнати та сусідів.
- [x] Кімнатні чати з текстовими повідомленнями у SQL.
- [x] Перегляд паркінгу, факультетів, навчальних курсів, вакансій та заявок на вакансії.
- [x] Оголошення та події: підключити замість поточних заглушок.
- [x] Адміністративні операції: управління мешканцями, кімнатами, поселеннями та зверненнями.
- [x] Видалено локальні мок-дані та демонстраційне наповнення SQL; довідники звернень читаються з PostgreSQL.

Реалізовано базовий адміністративний кабінет у межах свого гуртожитку: створення й редагування
мешканців, блокування з причиною, кімнати з місткістю та доступністю, поселення / переселення /
виселення з історією, опрацювання звернень зі статусами й відповідями. Оголошення та події
зберігаються у PostgreSQL; адміністрація керує публікаціями, мешканці реєструються на події.
Детальніші завдання нижче (окремі місця, продовження, майстри, ролі, сповіщення тощо)
залишаються наступними етапами.

Дата народження вже є в `users.date_of_birth`; потрібно додати її до інтерфейсу. Таблиця `applications` зараз описує заявки на вакансії — звернення щодо проживання й ремонту мають бути окремими сутностями.

## 3. Ролі та права

| Роль | Можливості | Межі доступу |
| --- | --- | --- |
| Мешканець | Власний профіль, кімната, звернення, чати, оголошення, події | Власні дані та доступні спільні матеріали |
| Адміністратор гуртожитку | Мешканці, кімнати, поселення, оголошення, звернення, локальні ролі | Лише призначені йому гуртожитки |

- [ ] Розділити глобальні ролі й призначення в конкретному гуртожитку.
- [ ] Адміністратор може призначити дозволену локальну роль.
- [ ] Зміна власного профілю не дозволяє змінювати роль, статус акаунта чи поселення.
- [ ] Перевіряти права в операціях з даними, а не лише приховувати кнопки.
- [ ] Записувати зміну ролей, блокування, поселення та виселення в журнал дій.

## 4. Архітектура та робота з SQL

Поточний інтерфейс можна розвивати на CustomTkinter. Для використання на кількох комп’ютерах цільова схема: **CustomTkinter → серверний API → PostgreSQL**. Облікові дані бази залишаються на сервері; клієнт отримує лише дозволені дані. Вебінтерфейс або мобільний клієнт можна додати пізніше через той самий API.

- [ ] Відокремити UI, правила роботи й SQL-запити, щоб логіка поселення не залежала від віджетів.
- [ ] Перед розповсюдженням застосунку винести автентифікацію, права та операції з базою в серверний API.
- [ ] Використовувати тільки PostgreSQL як джерело даних; не підставляти мок-дані при помилці підключення.
- [ ] Для порожніх таблиць показувати порожній стан, для недоступної БД — зрозумілу помилку та повторне завантаження.
- [ ] Запровадити послідовні SQL-міграції в `migrations/` зі збереженням наявних даних.
- [ ] Відокремити створення схеми, початкове налаштування й демонстраційні записи. Нинішній `db.sql` починається з `DROP TABLE` і не підходить для оновлення робочої бази.
- [ ] Використовувати параметризовані SQL-запити, обмеження цілісності та транзакції для пов’язаних змін.
- [ ] Завантажувати дані без блокування вікна; оновлювати віджети в головному потоці UI.

## 5. Етап 1 — акаунти та адміністративний кабінет

Мета: адміністрація керує реальними користувачами, а кожен мешканець має власний доступ.

- [ ] Додати окреме меню адміністратора з розділами «Мешканці», «Кімнати», «Поселення», «Звернення».
- [ ] Реалізувати список мешканців із пошуком та фільтрами за гуртожитком, кімнатою і статусом.
- [ ] Додати створення або запрошення мешканця адміністрацією без автоматичного поселення.
- [ ] Показувати дату народження; дозволити редагування лише передбачених полів профілю.
- [ ] Додати призначення ролей, блокування та розблокування із зазначенням причини.
- [ ] Замінити тимчасовий вхід на email і пароль, з хешуванням паролів, відновленням доступу та обмеженням спроб входу.
- [ ] Реалізувати серверні сесії, завершення сесій при блокуванні та перевірку актуальних прав.
- [ ] Призначати першого головного адміністратора окремою процедурою налаштування; не підвищувати автоматично першого користувача, який увійшов.

Готовність: мешканець не може відкрити адміністративні операції, адміністратор одного гуртожитку не може змінювати інший, блокування припиняє доступ, зміни зберігаються після перезапуску.

## 6. Етап 2 — кімнати, місця та життєвий цикл проживання

Мета: система показує фактичну зайнятість і зберігає історію проживання.

- [ ] Додати управління гуртожитками, поверхами, кімнатами й окремими місцями в кімнаті.
- [ ] Визначити місткість, доступність місця та можливість закрити кімнату на ремонт.
- [ ] Реалізувати поселення, переселення й виселення з датою, причиною та відповідальним працівником.
- [ ] Зберігати історію поселень замість перезаписування лише `students.room_id`.
- [ ] Заборонити подвійне поселення на одне місце та одночасне активне проживання мешканця у двох місцях. Захистити також одночасні запити двох адміністраторів.
- [ ] Виводити вільні місця, поточних мешканців та історію конкретної кімнати.
- [ ] Оновлювати доступ до кімнатного чату після зміни поселення; колишній мешканець втрачає доступ до чату попередньої кімнати.
- [ ] Додати очікувану дату завершення навчання й окрему дату завершення проживання.
- [ ] Перед завершенням проживання створювати нагадування та можливість подати заявку на продовження, зокрема при вступі на магістратуру.
- [ ] Продовження підтверджує адміністрація. Випуск сам по собі не видаляє акаунт: проживання завершується окремою операцією, історія зберігається.

Готовність: адміністрація проводить повний цикл «поселити → переселити → продовжити → виселити», а зайнятість, історія й доступи залишаються узгодженими.

## 7. Етап 3 — звернення та ремонтні заявки

- [ ] Створення звернення з категорією, описом, кімнатою / місцем проблеми та пріоритетом.
- [ ] Категорії: сантехніка, електрика, меблі, інтернет, прибирання, інше.
- [ ] Статуси: «Нова» → «Прийнята» → «В роботі» → «Виконана» → «Закрита»; окремо — скасування з причиною.
- [ ] Призначення відповідального майстра, терміну та історія зміни статусів.
- [ ] Коментарі мешканця й працівника; внутрішні коментарі адміністрації з окремим доступом.
- [ ] Підтвердження результату мешканцем або повторне відкриття, якщо проблему не усунено.
- [ ] Фільтри для адміністрації та повідомлення про нові, прострочені й виконані заявки.
- [ ] Додавання фотографій після реалізації захищеного зберігання вкладень.

Готовність: мешканець створює заявку, адміністрація призначає майстра, майстер фіксує виконання, мешканець бачить усю доступну йому історію.

## 8. Етап 4 — оголошення, сповіщення та події

- [ ] Оголошення для всього гуртожитку, поверху або конкретної кімнати.
- [ ] Створення, редагування, закріплення, архівування та дата завершення публікації.
- [ ] Позначка важливості й підтвердження прочитання важливих оголошень.
- [ ] Центр сповіщень: нова заявка, зміна статусу, оголошення, наближення завершення проживання.
- [ ] Події з датою, місцем, описом, кількістю місць і реєстрацією учасників.
- [ ] Налаштування необов’язкових сповіщень; зовнішні канали повідомлень — після стабільної роботи внутрішнього центру.

Готовність: адресати бачать свої оголошення та сповіщення, а користувачі іншого гуртожитку не отримують закриті публікації.

## 9. Межі першого релізу — MVP

До MVP входять етапи 1–3, оголошення та базові внутрішні сповіщення з етапу 4. Наявні текстові кімнатні чати залишаються частиною продукту. Розширені події, медіачати, оплати й мобільний клієнт не блокують цей реліз.

Ключовий сценарій приймання: головний адміністратор призначає адміністратора гуртожитку → адміністратор запрошує мешканця й поселяє його → мешканець входить, бачить кімнату та оголошення, створює ремонтну заявку → працівник виконує її → адміністрація оформлює продовження або виселення.

## 10. Після MVP

### Чати й спільнота

- [ ] Чати гуртожитку та групи за інтересами, створення груп і запрошення учасників.

- [ ] Ліміти частоти й довжини повідомлень, захист від спаму та перевірка членства при кожній операції.
- [ ] Непрочитані повідомлення, пошук та завантаження історії частинами.
- [ ] Фото, файли та GIF: обмеження розміру й типів, перевірка вмісту, закритий доступ до завантаження.

### Послуги та фінанси

- [ ] Бронювання паркомісць, пральні та спільних приміщень без перетину бронювань.

- [ ] Звірка платежів, квитанції та експорт звітів. Інтеграцію онлайн-оплат планувати окремо після визначення правил обліку.

### Управлінські звіти та додаткові модулі

- [ ] Завантаженість гуртожитків, вільні місця, строки завершення проживання.
- [ ] Статистика звернень, прострочення та час виконання.
- [ ] Експорт дозволених даних із журналюванням операції.
- [ ] Курси, факультети й вакансії розвивати після основних процесів проживання; залишити їх окремими модулями.
- [ ] Вебінтерфейс для мешканців і працівників; мобільний доступ — наступним кроком за потребою.

## 11. Розвиток структури PostgreSQL

Назви нижче — пропозиція для проєктування міграцій, а не вже створені таблиці.

| Сутності | Призначення |
| --- | --- |
| `users`, `roles`, `user_roles`, `dorm_admins` | Акаунти, глобальні ролі та локальні призначення без двох незалежних джерел однакових прав |
| `auth_sessions`, `account_invitations`, `password_reset_tokens` | Сесії, запрошення та відновлення доступу; токени з обмеженим строком дії |
| `dorms`, `rooms`, `room_places` | Гуртожитки, кімнати та конкретні місця |
| `residencies`, `residency_extension_requests` | Історія проживання та заявки на продовження |
| `maintenance_requests`, `request_comments`, `request_status_history` | Ремонтні заявки, обговорення та історія виконання |
| `announcements`, `announcement_reads` | Публікації, адресати та підтвердження прочитання |
| `notifications` | Персональні сповіщення та стан прочитання |
| `chats`, `chat_members`, `messages`, `attachments` | Розширення поточних кімнатних чатів без втрати історії |
| `events`, `event_registrations` | Події та реєстрації |
| `audit_log` | Хто, коли та яку адміністративну дію виконав |

Для кожної міграції визначити зовнішні ключі, індекси під реальні запити, правила видалення, часові поля та перевірки цілісності. Перехід від `students.room_id` до історії проживання має включати перенесення наявних поселень і переведення всіх запитів на нове джерело даних.

## 12. Надійність і перевірка перед релізом

- [ ] Інтеграційні перевірки на окремій PostgreSQL-базі з тестовими записами; робоча програма не використовує мок-дані.
- [ ] Перевірка прав для мешканця, майстра, адміністратора іншого гуртожитку та заблокованого акаунта.
- [ ] Перевірка одночасного поселення на одне місце, переселення та відкликання доступу до старого чату.
- [ ] Перевірка міграцій на копії попередньої схеми зі збереженням даних.
- [ ] Перевірка помилок мережі: повторний запит не повинен створювати дубль поселення чи звернення.
- [ ] Резервне копіювання та перевірене відновлення бази; журнал помилок без паролів і токенів.
- [ ] Обмежити видимість персональних даних, визначити строки зберігання й процедуру архівування / видалення.
- [ ] Перевірити повний основний сценарій після перезапуску клієнта й сервера.

## 13. Найближчі завдання в цьому репозиторії

1. Підготувати недеструктивні міграції та відокремити демонстраційне наповнення від робочої схеми.
2. Зафіксувати модель ролей і перевірки доступу, додати адміністративне меню та список мешканців.
3. Додати дату народження до профілю та картку мешканця для адміністрації.
4. Реалізувати кімнати, місця й історію поселень; перевести кімнату та чати на актуальне проживання.
5. Створити серверний API та повноцінний вхід перед використанням з кількох комп’ютерів.
6. Додати ремонтні заявки, оголошення та внутрішні сповіщення.
7. Перевірити сценарій MVP на окремій базі й провести пробне використання в одному гуртожитку.

План визначає порядок робіт без календарних обіцянок: оцінювати строки кожного етапу після деталізації його екранів, SQL-міграцій і сценаріїв приймання.
